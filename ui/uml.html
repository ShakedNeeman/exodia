High-level design

A catalog in front of an object store. The assignment asked for reliable terabyte ingest, user metadata at upload, automatic technical enrichment, and a logical way to browse. These diagrams are the architecture overview: components, how they talk, and where data lives at each stage.

docs/uml.md · docs/uml.he.md

Reliable TB uploadsPresigned multipart to S3. The API never carries file bytes.
Metadata at uploadUser fields are committed in draft, before the first part lands.
Enrich where possibleAsync plugin workers. Unknown types stay first-class.
Logical browseCollections and facets — not a reconstructed filesystem.

3. Class diagram — where data lives

An asset is logical. An object is physical. User metadata is intent. Technical metadata is observation.

Collection

  • id, name, acl
  • logical browse root

Asset

  • id, title, state, family
  • size, created_by
  • what people browse

AssetObject

  • role: primary | sidecar
  • storage_key, checksum
  • what S3 holds

UploadSession

  • multipart_upload_id

UserMetadata

  • tags, fields, path

4. State machine — the asset

draft→ uploading→ uploaded→ enriching→ ready / partial · failed

Download is allowed from uploaded onward. Enrichment never hides the file. partial means at least one extractor failed or the type is unknown. failed is integrity / session only.

6. Decisions I would not reverse

Control plane ≠ data planeBytes never go through the API. S3 assembles parts; we decide when to Complete. S3 does not run SQL transactions and does not manage video.
Asset ≠ objectA SIGMF take is one catalog row and two blobs. Zip-at-ingest would break range reads.
Enrichment is best-effortThe brief says “where possible”. Unknown is a type. A failed parser does not hide the file.
Browse is a catalogCollections + facets + saved views. The old path is a filter, not the product.
